# サッカー分析AI - 実データ連携用プロキシサーバー

「世界一分かりやすいサッカー分析AI」の `index.html` を、有料の実データAPI(API-Football)に
安全に接続するための、最小限のバックエンドです。

## なぜバックエンドが必要か

これまでの `index.html` は単一ファイルだけで完結していました。しかしAPI-FootballのAPI
キーをHTML/JSに直接書いてしまうと、ページのソースコードを見れば誰でもキーを盗み見・
悪用できてしまいます。このサーバーはキーを `.env`(サーバー側のみ、ブラウザには一切
送られません)に保持し、フロントエンドからは `/api/...` という自前のエンドポイントだけを
呼ばせることで、キーを外部に晒さずに実データを取得できるようにします。

### ファイルの置き場所について

`server.js` は、自分と同じフォルダ・1つ上のフォルダのどちらに `index.html` があっても
自動的に見つけてトップページとして配信します。そのため、次のどちらの置き方でも
動作します。

- GitHubリポジトリの直下に `server.js` と `index.html` を一緒に置く(このリポジトリの
  現在の構成)
- `server/` フォルダの中に `server.js` を置き、`index.html` は1つ上のフォルダに置く
  (ローカルで動作確認する時の構成)

`index.html` がどちらの場所にも無い場合(バックエンドのAPIだけを動かしたい場合)は、
トップページは404になりますが、`/api/...` の各エンドポイントは問題なく動作します。

## セットアップ手順

### 1. API-FootballのAPIキーを取得する

1. https://dashboard.api-football.com/register で無料アカウントを作成
2. ログイン後のダッシュボード「My Access」にAPIキーが表示されます
3. まずは無料プラン(100リクエスト/日)で動作確認し、実運用する場合は
   Pro($19/月・7,500リクエスト/日)以上への切り替えを推奨します
   (料金・上限は変わる可能性があるため、契約前に公式サイトで最新情報をご確認ください)

RapidAPI経由でキーを取得した場合は、`.env` の `API_FOOTBALL_VIA_RAPIDAPI` を `true` に
してください(認証ヘッダーの形式が変わります)。

### 2. 起動する(npm installは不要です)

このサーバーは外部パッケージを一切使わず、Node.js標準機能だけで書かれています。
Node.js(18以上)さえパソコンに入っていれば、`npm install` なしでそのまま起動できます。

```bash
cd server
cp .env.example .env
# .env を開いて API_FOOTBALL_KEY にキーを貼り付ける(RapidAPI経由で取得した場合は
# API_FOOTBALL_VIA_RAPIDAPI=true にする)
node server.js
```

Node.jsが入っているか確認したい場合は `node -v` を実行してください。18以上の
バージョン番号(例: v20.11.0)が表示されればOKです。入っていない場合は
https://nodejs.org/ からインストールしてください。

起動後、ブラウザで `http://localhost:8787/` を開いてください。`index.html` もこの
サーバーが自動的に配信するので、これまで通り1つのURLで動作します。
(直接 `index.html` をダブルクリックして開いた場合は `/api/...` に届かずシミュレーション
表示のままになるので、必ず `http://localhost:8787/` の方を開いてください。)

### 3. 動作確認

- `http://localhost:8787/api/health` にアクセスし、`"hasKey": true` になっていればキー設定はOK
- 選手プロフィール画面の「📈 コンディション・パフォーマンス推移」に、実データが取得できた
  選手は「🟢 実データ(API-Football)」というバッジ付きのセクションが追加表示されます
  (取得できなかった選手は、これまで通りAIシミュレーション表示のみになります)
- 「⚽ 試合分析AI」タブに、本日の実際の試合がAPI経由で見つかった場合は
  「📡 本日の実際の試合」という一覧が追加表示されます

### 4. AI予測の実績を記録する(任意・無料)

ホーム画面には「🤖 AI予測の実績」という欄があり、AIが実際に出した予測(API-Footballの
本物の予測データ)と実際の試合結果を突き合わせて、本当の的中率を表示します。架空の
数字を出さないため、この機能には無料の外部ストレージ「Upstash Redis」への接続が
必要です。設定しなくてもアプリ自体は問題なく動作します(その場合は「これから記録を
開始します」という正直な表示になるだけです)。

1. https://console.upstash.com/ にアクセスし、無料アカウントを作成
   (Email / GitHub / Google のいずれかでサインアップ可能。クレジットカード不要)
2. ログイン後「Create Database」→ 名前を適当に付けて(例: soccer-ai)作成
   (Type は「Regional」、リージョンは近い場所でOK。無料プランのままで十分です)
3. 作成したデータベースの画面内、「REST API」という項目までスクロール
4. 「UPSTASH_REDIS_REST_URL」と「UPSTASH_REDIS_REST_TOKEN」という2つの値をコピーし、
   `.env`(本番はRenderの環境変数)の同名の項目に貼り付ける
5. サーバーを再起動すると、コンソールに「AI予測の記録(Upstash Redis): あり」と
   表示されます

記録の仕組み:
- ユーザーが「試合分析AI」で今後の試合を1回見るたびに、その試合のAI-Football側の
  実際の予測(勝率%)を1回だけ記録します(架空の予測ロジックではなく、実データに
  基づく予測をそのまま採用しています)
- その試合が終了した後、ユーザーが再びその試合(または「今日の試合」一覧)を見た
  タイミングで、実際の結果と予測を突き合わせて的中/不的中を確定します
- 無料プランは月50万コマンドまで無料(このアプリの規模であれば十分すぎるほど余裕が
  あります)で、クレジットカードを登録しない限り自動課金される心配もありません

### 5. 誰もサイトを見ていなくても自動で記録を貯める(任意)

上記までの設定だけでは、「AI予測の実績」は**誰かが実際にそのページを見た時だけ**
記録・確定されます(見た人がいなければ、試合が終わっても正答率は更新されません)。
ログインなし・アクセスなしでも自動的に記録を貯めたい場合は、`GET /api/predictions/auto-collect`
というエンドポイントを用意しています。これを定期的に(例: 4時間おきに)外部から
呼び出してもらうことで、サーバー自身に常駐タイマーを置かなくても自動収集ができます
(無料ホスティングはアイドル時にスリープしますが、この定期アクセス自体がスリープ
復帰のきっかけにもなります)。

呼び出すたびに、次の2つを行います:
- まだ結果が確定していない予測を、実際の試合結果と照合して確定する(1回の実行で
  最大8件まで。頻度が上がるほど積み残しは早く解消されます)
- 今日の試合のうち、まだ記録していない試合を新たに数件(最大3件)記録する

API-Footballの無料枠(1日100リクエスト)を使い切らないよう、1回あたりの件数に
上限を設けています。

**推奨: シークレットキーを設定する**
このエンドポイントは(見た目上は)誰でも呼び出せてしまうため、悪意ある連打で
API-Footballの無料枠を消費されるのを防ぐには、`.env`(本番はRenderの環境変数)に
`AUTO_COLLECT_SECRET=好きな英数字の文字列`を追加してください。設定すると、
`/api/predictions/auto-collect?key=設定した文字列` のように`key`パラメータが
一致した場合のみ動作するようになります(未設定の場合は誰でも呼び出せる状態の
ままです)。

**定期的に呼び出す方法(推奨: GitHub Actions・追加登録不要):**
このリポジトリには `.github/workflows/predictions-auto-collect.yml` が同梱されて
おり、6時間おき(1日4回)に自動でこのエンドポイントを呼び出す設定が既に入って
います(`daily-learning.yml`と同じ仕組み)。有効にするには、リポジトリの
Settings → Secrets and variables → Actions で以下の1つを追加登録するだけです
(`LEARNING_SECRET_KEY`は`daily-learning.yml`用に既に登録済みのものをそのまま
使います)。
- `AUTO_COLLECT_ENDPOINT_URL` : 例) `https://あなたのRenderのURL/api/predictions/auto-collect`

**その他の方法(いずれでもOK・すべて無料):**
- 外部の無料cronサービスを使う: [cron-job.org](https://cron-job.org/)
  や [UptimeRobot](https://uptimerobot.com/) に無料登録し、「4時間おきに
  `https://あなたのRenderのURL/api/predictions/auto-collect?key=設定した文字列`
  にアクセスする」だけの設定を1つ作成する。コード不要、画面操作だけで完了します。
- このプロジェクトを一緒に作っているAIアシスタント(このチャット)に、定期実行の
  スケジュールタスクを設定してもらう(このアシスタントのセッション上の仕組みに
  依存するため、GitHub Actionsや外部cronサービスの方が長期的には独立性が高く
  おすすめです)。

**「毎日たくさん試合があるのに件数が全然増えない」場合について:**
API-Footballの無料プラン(1日100リクエスト)を使い切らないよう、1回の実行で
新規に記録できる試合数はあえて少なめ(最大3件)に制限してあります。1日4回の
実行でも1日最大12件程度が上限です。世界中の試合をもっと網羅的に・素早く
記録したい場合は、①`predictions-auto-collect.yml`のcron間隔を短くする、
②API-Footballを有料プラン(Pro: $19/月・7,500req/日)に切り替えた上で
サーバー側の`AUTO_COLLECT_LOG_CAP`/`AUTO_COLLECT_RESOLVE_CAP`の上限値も
引き上げる、のいずれかの対応が必要です(無料プランのままでは、件数を大幅に
増やすとAPI-Footballの利用上限に引っかかり、他の機能(選手検索・試合分析など)
にも影響が出るおそれがあります)。

### 6. AI対話エンジン(議論モード)を有効にする(任意・費用が発生します)

【Stage B・NEW】「⚽ 試合分析AI」等の予測がAPI化されたのに続き、【Stage C・NEW】として
「〜だと思う」「なぜ？」のような意見・考察を求める質問に、AIが実データを根拠に
本物の考察を返す「議論モード」を追加しました。単純な質問(選手データ・順位・試合結果
など)はこれまで通りルールベースで即答し、この機能は一切使いません(費用もかかりません)。
意見・考察・仮説を求める質問のときだけ、実際の生成AI(LLM)を呼び出します。

設定しなくてもアプリ全体は問題なく動作します(その場合は「LLMのAPIキーが設定されて
いないため、考察機能はまだ利用できません」という正直な表示になり、代わりに従来通りの
データ要約が「参考情報」として表示されます)。

1. https://console.anthropic.com/ にアクセスし、アカウントを作成する
2. 支払い方法を登録する(**ここだけは他の設定と違い、クレジットカードの登録と
   従量課金が必要です**。使った分だけ請求される仕組みで、月あたりの利用上限を
   Anthropicのコンソール側でも設定できます)
3. 左メニューの「API Keys」→「Create Key」でキーを発行し、コピーする
4. `.env`(本番はRenderの環境変数)の `ANTHROPIC_API_KEY` に貼り付ける
5. 併せて、コストの暴走を防ぐ安全装置(2段階)を設定できます。詳しくは
   `.env.example` を参照してください。
   - `PER_IP_LLM_CALLS_PER_DAY`(利用者ごとの1日あたり上限。既定10回): 世界中の
     誰でも使える公開サービスを想定し、一人(または悪意あるアクセス)がその日の
     予算を独り占めして、他の利用者が誰も使えなくなる事態を防ぎます。
   - `MAX_LLM_CALLS_PER_DAY`(サイト全体の1日あたり上限。既定2000回): ①をすり
     抜けるような異常アクセスからサービス全体を守る、最後の安全弁です。
   - いずれの上限に達した場合も、それ以上はLLMを呼び出さず、正直にその旨を
     表示するだけです(上限を超えて課金されることはありません)。
   - **さらに安心したい場合**: 上記はあくまでこのアプリのコード側の安全装置です。
     Anthropic Console(https://platform.claude.com/ → 組織の設定 → 請求)側でも
     「使用量上限」を別途設定しておくことを強く推奨します。アプリ側の仕組みが
     万が一機能しなくても、設定した金額以上は絶対に請求されなくなります。
6. サーバーを再起動すれば設定完了です

**将来、Claude以外のAIに乗り換えたい場合:** `.env` の `LLM_PROVIDER` を
`openai` / `gemini` / `openrouter` / `local` に変更するだけで、他のコードを
一切変更せずに切り替えられる設計にしています(ただし現時点でフル実装されている
のは `anthropic` のみです。他の値は `server/llm/providers/` にプレースホルダーが
あり、実装が済むまでは「まだ実装されていません」というエラーになります。実機で
確認していない実装を「動く」と偽って提供しないための、意図的な仕様です)。

### 7. 毎日学習エンジン(Learning Engine)を有効にする(任意・無料)

【Stage D・NEW】このAIは「聞かれたら考えるAI」から一歩進んで、「毎日、登録クラブの
実際の試合結果を見て、事実を蓄積し、独自の予測モデルを検証・改善していくAI」を
目指しています。これを実現するのが `POST /api/learning/run-daily` です。

**これが実際に行うこと(正直な説明):**
1. 登録している約11クラブについて、直近の実際の試合結果(API-Football)から、
   フォームの変化(直近5試合 vs その前5試合の得失点差)を計算し、意味のある変化が
   あった場合だけ「事実」として記録する(変化が無ければ何も記録しません)
2. このアプリ独自の実験的な予測モデル(ホームアドバンテージの大きさ・フォーム差への
   感度、という2〜3個の解釈可能なパラメータだけで勝敗を予測する統計モデルで、
   ディープラーニングではありません)が、登録クラブの直近の試合について予測を立てる
3. 過去に立てた予測のうち、試合が終わっているものを実際の結果と照合して的中/不的中を
   記録する
4. 十分な検証データ(10件以上)が溜まったら、実データに対して「今のパラメータ」と
   「少しだけ変えたパラメータ」の的中率を両方計算し、本当に的中率が上がる場合だけ
   パラメータを更新する(悪化する変更は採用しません)
5. これらすべての結果を「成長ログ」として記録し、ホーム画面の「🧠 昨日学んだこと」に
   実際の数字として表示する

**この「自社予測モデル」と、既存の「AI予測の実績」ウィジェットとの違い:** ホーム画面の
「AI予測の実績」は、あえてこのアプリ独自のロジックではなく、API-Football自体が
提供する本物の予測(`/predictions`)の的中率を記録する設計でした(検証しようが
ない自作ロジックを実績として見せないため)。今回の学習エンジンは目的が異なり、
「このアプリ自身のモデルを、実データで検証しながら本当に育てる」実験です。混同を
避けるため、記録も表示もはっきり別物として分けています。

**セットアップ(2ステップ):**
1. `AUTO_COLLECT_SECRET`(手順5で設定したもの)を、このエンドポイントの保護にも
   流用します。追加の設定は不要です。
2. 毎日決まった時間に自動実行したい場合は、このリポジトリに含まれる
   `.github/workflows/daily-learning.yml` を使います。GitHubの「Settings → Secrets
   and variables → Actions → New repository secret」から、`LEARNING_ENDPOINT_URL`
   (例: `https://あなたのRenderのURL/api/learning/run-daily`)と`LEARNING_SECRET_KEY`
   (`AUTO_COLLECT_SECRET`と同じ値)を登録するだけで、毎日自動的に実行されます
   (新しいアカウント登録は不要・完全無料です)。「Actions」タブから手動実行して
   動作確認することもできます。

**API-Football無料枠への配慮:** 1回の実行で使うリクエスト数は、登録クラブ数(11)に
比例するよう意図的に絞っています(だいたい数十リクエスト程度)。無料枠は1日100
リクエストなので、通常のユーザー利用分の余力も残る設計です。

### 8. Knowledge Engine / Memory Engine / Hypothesis Engine(Stage E・NEW)を理解する

【Stage E】Stage Dの「学習エンジン」は予測モデルの的中率を改善するものでしたが、
Stage Eはそれとは別に「AIの知識と考え方そのものが日々深まっていく」ことを目指した
拡張です。新しく4つのモジュールを追加し、`POST /api/discuss`(議論モード)に
組み込みました。追加の環境変数設定は不要です(既存のUpstash Redis・API-Footballの
設定をそのまま使います)。

**① Knowledge Engine(`server/knowledge/knowledgeStore.js`)** ― 「事実(fact)」
「分析(analysis)」「意見(opinion)」を明確に分けて保存する知識ベースです。内容の
ハッシュ値で重複を判定し、全く同じ内容は二重登録しません(観測日だけ更新)。
**2026年8月の拡張(下記「9. Knowledge Engine 4層構造」参照)で、`profile`(固定知識)・
`reflection`(振り返り)の2種類を追加し、正式に4層構造になりました。** 有効期限は
fact=14日・analysis=30日・opinion=7日(以前は3日でしたが、Layer3が「AIの毎日の見解」を
担う設計に合わせて延長しました)・profile=60日・reflection=90日で、それぞれ
「アクティブな知識」の一覧から自動的に外れます(削除はせず、履歴としては残ります)。

**② Memory Engine(`server/memory/memoryStore.js`)** ― 議論モードでAIが導いた
「今の結論」をクラブごとに記憶します。次に同じクラブについて聞かれたとき、結論が
前回と同じなら「変わっていない」、変わっていれば「なぜ変わったか」を一緒に記録します
(`POST /api/discuss`のレスポンスの`meta.reasoning.memory`で確認できます)。

**③ Reasoning Engine(`server/reasoning/`)** ― 回答を書く前に、AIが内部的に
「複数の説明の可能性(仮説)」を検討する仕組みです。具体的には
`hypothesisGenerator.js`が常に3つの観点(①負傷・出場停止 ②直近フォーム・
フォーメーション ③移籍による戦力変化)から仮説を立て、`evidenceRanking.js`が
実際に取得できた根拠の量と質(事実=1.0点、検証済み分析=1.5点、AIの意見=0.5点)で
スコア化し、最も根拠が強い仮説を選びます。`reasoningEngine.js`が仕上げとして
「根拠は十分か」「他の可能性も検討したか」「反対意見はあるか」を内部的に自己確認し、
その結果を(利用者には見せない内部情報として)LLMへのプロンプトに含めます。

**④ Knowledge Graph(`server/knowledge/relationshipIndex.js`)** ― 「このクラブの
現在の監督は誰か」「直近のフォーメーションは何か」のような一方向の関係を保存する、
最小限の関係インデックスです。

**正直にお伝えしたい設計上の判断(ご要望に対する開示):**
- **知識の取得元について**: クラブ公式サイト・ニュース記事・監督の生の発言を
  スクレイピングする機能は、今回あえて実装していません。任意の外部サイトを無断で
  スクレイピングすることには利用規約・著作権上のリスクがあるためです。現時点では、
  このアプリが既に契約しているAPI-Football(実データAPI)からの情報と、そこから
  AI自身が導き出した分析に限定しています。将来、利用規約上問題のない具体的な
  ニュースソースを決めていただければ、専用のfetcherを追加する形で拡張できます。
- **Hypothesis Generator / Evidence Rankingについて**: LLMを呼び出すのではなく、
  あらかじめ用意した観点テンプレートに実データを機械的に当てはめるルールベースの
  実装です。質問1件ごとに複数のLLM呼び出しを追加すると、このプロジェクトが最優先
  としている「コスト最適化」に反するため(現状: 1質問あたりのLLM呼び出しは
  従来通り1回のまま)。仮説の内容自体は固定でも、実際にどれだけ根拠が集まるかは
  毎回の実データ次第なので、「根拠に基づいて選ばれる」という実質は保たれています。
- **Knowledge Graphについて**: 本格的なグラフデータベース(複雑な探索ができるもの)
  ではなく、Upstash Redis上の単純なキー・バリューによる「一方向の関係の保存」に
  留めています。「このクラブの監督は誰か」は分かりますが、「この監督が率いた
  クラブを全部教えて」のような逆方向の探索はできません。
- **Hypothesis Engineと自社予測モデルの関係**: `server/learning/dailyJob.js`が
  新しい自社予測を立てる際、「なぜその予測なのか」を状態仮説として一緒に記録し、
  試合結果が出た時点でその仮説が当たっていたかを検証します。当たっていれば
  Knowledge Engineに「検証済みの分析」として昇格させ、外れていれば知識としては
  保存せず正直に破棄します(成長ログの`hypothesesConfirmed`/`hypothesesDiscarded`
  で件数を確認できます)。
- **既存の`learn:facts:*`保存のリファクタリング**: 従来アドホックに`learn:facts:*`
  というRedisキーへ直接読み書きしていた「事実」の保存は、今回すべてKnowledge
  Engine経由に統一しました。これにより重複排除・失効管理が正式に効くようになって
  います(以前は同じ内容を何日分も無制限に貯め続ける設計でした)。

### 9. Knowledge Engine 4層構造 / Prediction Engine v2 / 「AIマッチ分析」(2026年8月・知識拡張フェーズ)

ご要望「AIを"知識を蓄積する分析AI"へ進化させる」への対応として、Knowledge Engineを
4層構造に再編し、Prediction Engineに新しい特徴量と学習の仕組みを追加し、その結果を
利用者が見られる「AIマッチ分析」カード(`index.html`のホーム画面、`GET /api/match-analysis`)
を新設しました。追加の環境変数設定は不要です(既存のUpstash Redis・API-Football・
Anthropic APIキーの設定をそのまま使います)。

**Knowledge Engineの4層(`server/knowledge/knowledgeStore.js` / `server/knowledge/clubProfileEngine.js`):**
- **Layer1「事実」(`fact`)** ― 従来通り。毎日、登録クラブの実際の試合結果(API-Football)
  から機械的に抽出される客観的な数値の変化。既定14日で失効。
- **Layer2「固定知識」(`profile`)** ― NEW。クラブの戦術傾向・フォーメーション傾向・
  強み弱み・ビルドアップ・プレッシング・セットプレーの特徴を、実データ(直近フォーム・
  得失点)を根拠にLLMが生成します。API-Footballにはこの種の定性的な情報が無いため、
  保存する際は必ず`isAiGenerated:true`かつ「AIによる推定」と明示し、実データと混同
  しないようにしています。既にプロフィールがあるクラブは再生成しません(コスト最適化・
  既定60日で自動的に作り直し)。**`server/knowledge/clubProfileEngine.js`が担当。**
- **Layer3「AIの現在の見解」(`opinion`)** ― 拡張。毎日学習エンジンが、その日の実データ
  (フォームスコア・得失点・過密日程)を根拠に、クラブについての1文の見解をLLMに
  生成させます(例:「バイエルンは守備の安定感が増している」)。前回の見解と比べて
  変わった場合、変化理由もMemory Engine(`server/memory/memoryStore.js`)に記録します
  ―― これが「昨日何を考えていたか・今日何を考えているか・その理由」のご要望への回答です。
  Knowledge Engineにもミラー保存し、議論モードのRAGから検索できるようにしています。
- **Layer4「振り返り」(`reflection`)** ― NEW。試合が終わって予測を検証したタイミングで、
  「予想→結果→なぜ当たったか/なぜ外れたか→改善点」を**当たり・外れの両方について**必ず
  保存します(以前は外れた予測仮説を記録しておらず、なぜ外れたかを追跡できていません
  でした――このご指摘への直接の回答です)。LLMは使わず、実際に計算した特徴量と、その
  予測を立てた時点の重みだけから機械的に文章を組み立てます(`buildReflectionText`関数。
  でっち上げを避けるため)。既定90日保持。

**Prediction Engine v2(`server/learning/predictionModel.js` / `server/learning/features.js`):**
既存のv1(ホームアドバンテージ+フォーム差のみ)は変更せず、そのまま残しています
(既存のテスト・挙動を壊さないため)。v2はこれに追加する形の上位互換モデルです。

- **追加した特徴量**(すべて実データから計算。AIの推測は混ぜません): 得点力・失点率
  (直近試合の平均得点/失点)、負傷者数(`/injuries`)、順位・勝点(`/standings`)、
  過去対戦成績(`/fixtures/headtohead`)、過密日程(直近7日以内の試合数。疲労の代理指標)。
- **特徴量を追加するたびに重要度を学習する**というご要望への回答: 実際に解決した
  自社予測の記録に対して、ポワソン分布に基づく勝敗確率モデルの負の対数尤度を損失関数
  とした、数値微分による勾配降下法(`fitWeightsGradientDescent`)で各特徴量の重みを
  学習します。npm等の機械学習ライブラリは使わず素のJavaScriptで実装し、学習結果は
  必ずバックテストで「今より的中率が上回る場合のみ」採用します(過去のv1グリッド
  サーチと同じ安全策)。検証データが5件未満の場合は学習を試みません(過学習防止)。
  重みが未学習(0)の特徴量は、後述の★重要度で正直に「★0」と表示され、実際より
  重要そうに見せかけることはありません。
- **勝率・予想スコア**: ポワソン分布に基づき、実際に起こりうる全スコアの組み合わせ
  から「ホーム勝ち/引き分け/アウェイ勝ち」の確率と、最も確率が高いスコアライン
  (例:「1-0」)を算出します(単純にλの大小だけで決めるのではない、標準的な手法)。

**「AIマッチ分析」カード(`GET /api/match-analysis?home=クラブ名&away=クラブ名`、
`index.html`ホーム画面の「🧠 AIマッチ分析」カード)** ― ご要望の「単なる勝敗ではなく、
AIが試合を読むように」への回答です。任意の2クラブ(日本語名/英語名どちらも可)を
指定すると、その場でPrediction Engine v2と同じロジックを使い、次を返します。

1. AI勝率の内訳(例: レアル56% / 引分24% / バルサ20%)+確信度★
2. AIが最も重視した要素の★付きランキング(怪我★★★★☆ 等)+重み付けの割合(%)
3. 試合展開予想の文章(LLM設定時はLLMが実データを根拠に生成。未設定/日次予算超過時は
   決定論的な文章に自動フォールバックするため、機能自体は止まりません)
4. 「もし予想と違ったら」の逆シナリオ
5. 予想スコア付きの最終結論(例:「AIは1-0でレアル勝利と予想します。」)

このエンドポイントは`POST /api/discuss`と同じIPごとの日次LLM予算(既定10回/日)を
共有しますが、予算超過時もエラーにはせず、数値計算(勝率・★重要度・予想スコア)は
必ず返し、文章部分だけ決定論的な代替テキストに切り替えます。**正直な注意点**:
この分析は毎日学習エンジンの自動予測ループ(`learn:ownpred:*`)とは独立した、
都度(オンデマンド)の分析です。実際の試合結果との答え合わせ・学習(Layer4振り返り・
重みの再学習)は、毎日学習エンジンが自動登録した「登録クラブの次の試合」の予測に
対してのみ行われます(任意の2クラブの組み合わせは、まだ対戦カードが無い場合も
あり検証しようがないため)。

**実装できなかった項目と、その理由・代替案(ご要望への正直な回答):**
- **スタメン(先発メンバー)**: キックオフの約1時間前にならないと確定しないため、
  「1日1回のバッチ処理」という毎日学習エンジンの実行方式と原理的に噛み合いません
  (バッチは試合当日の早い時間に予測を作るため、その時点ではまだスタメンが発表
  されていません)。**代替案**: 「AIマッチ分析」はオンデマンドのため理屈上は
  キックオフ直前に呼び出せば間に合いますが、API-Football無料枠の消費が増えるため
  今回は見送りました。将来、有料プランへの移行と合わせて対応可能です。
- **移籍の試合への影響度**: API-Footballの`/transfers`は移籍の記録はありますが、
  「その移籍が今の実力にどれだけ影響しているか」を表す数値ではありません。安易に
  数値化すると根拠のない特徴量になってしまうため見送りました。**代替案**: 移籍の
  「有無」自体は事実としてKnowledge Engine(Layer1)に既存の仕組みで記録できます
  (影響度の数値化はしない)。
- **監督交代後の成績**: 「いつ監督が交代したか」を確実に取れるクリーンなフィールドが
  API-Footballに無く、`/fixtures/lineups`のcoach名の変化を日々突き合わせるような
  複雑な検出ロジックが必要になるため見送りました。**代替案**: 検出ロジックの仕様
  (例:「3日連続でcoach名が変わったら交代とみなす」等)を具体的にご指定いただければ、
  次回実装可能です。
- **ローテーション(疲労による選手起用の変化)**: スタメンと同じ理由(起用が確定
  するのが直前)で保留しました。**代替案**: 実装済みの「過密日程(直近7日の試合数)」
  を疲労の代理指標として採用しています(選手個別ではなくチーム全体の疲労度)。
- **xG(期待ゴール数)・xGA・PPDA**: 事前に調査した結果、API-Football側のxG
  カバー率はリーグによって「不安定」で、PPDAはそもそもデータとして提供されて
  いないことを確認しました(出典: API-Football比較記事)。存在しない数値を
  推定で埋めると「実データ」を偽ることになるため、実装していません。**代替案**:
  得点力・失点率(平均得点/失点)という、確実に取得できる実データで代用しています。
  将来、xG提供元の別APIと契約すれば追加できます。
- **選手個別の詳細プロフィール(利き足・市場価値・契約・怪我履歴等)**: 第一段階
  ではクラブ単位のLayer2固定知識(`clubProfileEngine.js`)のみを実装していましたが、
  **第二段階(下記「10.」参照)で選手版(`playerProfileEngine.js`)も実装しました。**
  ただし市場価値・契約・利き足はAPI-Football側にそもそもデータが存在しないため、
  引き続き未実装です(詳細は下記10.の「実装できなかった項目」参照)。

### 10. Knowledge Engineのさらなる拡張 / 選手Layer2 / オンデマンド知識補完 / Knowledge Graph強化(2026年8月・知識拡張フェーズ 第二段階)

第一段階に続き、「サッカーについて質問された時に、人間のアナリストより多くの情報を
持っているAI」というご要望に対応するため、以下を実装しました。

**① 「主要リーグ全クラブ・全選手」への現実的な対応方法(オンデマンド知識補完)**

「主要リーグの全クラブ・全選手について毎日更新」を、API-Football無料枠(1日100
リクエスト)は言うまでもなく有料プランでも、単純な総当たりバッチ処理で実現するのは
非現実的です(欧州5大リーグだけでも98クラブ・2,000名超の選手がおり、1クラブ/1選手
あたり複数回のAPI呼び出し+LLM生成が必要なため)。そこで、これまで登録11クラブに
限定していたKnowledge Engine Layer2(固定知識)の自動生成を、**議論モード
(`POST /api/discuss`)で実際に質問されたクラブ・選手についても、その場で生成し
キャッシュする**ように拡張しました(`server/rag/knowledgeSource.js`のensureClubProfile
呼び出し、選手は`server/knowledge/playerProfileEngine.js`)。これにより理論上は
"主要リーグの任意のクラブ・任意の選手"に対応でき、質問された相手から知識が
蓄積されていきます。一度生成されたプロフィールは既定60日キャッシュされるため、
2回目以降の質問では追加コストが発生しません。

**② 選手のKnowledge Engine(Layer1事実+Layer2プロフィール)**

これまで選手については「今シーズンの出場数・得点・アシスト・平均レーティング」
しか使っていませんでしたが、実はAPI-Football(`/players`)の同じレスポンスに
以下の実データが含まれていることが分かったため、追加のAPI呼び出し無しで
抽出するようにしました(`server/learning/playerFeatures.js`):
キーパス・パス成功率・ドリブル成功率・守備指標(タックル+インターセプト)・
デュエル(競り合い)勝率。これらは`GET /api/player-season-stats`のレスポンス、
および議論モードでの選手に関する質問の「事実」にそのまま反映されます。
その上で、プレースタイル・特徴・長所・短所だけをLLMに生成させ(Layer2、
必ず「AIによる推定」と明示)、実成績データを根拠にしています。

**③ 監督遍歴(Layer1実データ)+ Knowledge Graphの強化**

API-Footballに`/coachs`という専用エンドポイントがあり、監督ごとの在籍クラブ・
在任期間(career)を取得できることが分かったため、「監督遍歴」を実データとして
実装しました(`fetchCoachCareer`/`computeCoachCareer`、`server/learning/features.js`)。
これにより、Knowledge Graphに次のような一方向の関係が実データで記録されます:
`team→manager→formationTendency`(クラブの現在の監督→その監督の下でのフォーメーション
傾向)、`person→previousClub`(監督の前所属クラブ)。`getRelationChain`で
これらを2〜3ホップたどることができます。

正直な注記: ご要望の「レアル・マドリード→アンチェロッティ→4-3-3→ベリンガム→
右サイド攻略→クロス増加」のように、監督・フォーメーション・特定選手・特定の
攻撃パターンまで一気通貫でつながる連鎖は、今回実装した実データ(監督遍歴・
フォーメーション傾向)の範囲を超えています(「どの選手が」「どちらのサイドを」
「なぜ攻略できているか」は、API-Footballの実データからは導けない、非常に
具体的な戦術ジャーナリズムの領域であり、これをLLMに生成させると"それらしいが
検証できない"内容になってしまうため、あえて実装していません)。今回実装した
のは、それに至る手前の「team→manager→formationTendency」「person→
previousClub」という、実データに裏付けられた確実な連鎖です。より具体的な
戦術連鎖を再現したい場合、Layer3(AIの日々の見解)やLayer2のプロフィール文章の
中で言及されることはありますが、それは常に「AIによる推定」であり、Knowledge
Graphの正式な関係(setRelation)としては保存していません(検証可能性のない
関係を事実であるかのように保存しないため)。

**④ ホーム/アウェイの差(Layer1実データ)**

ホーム/アウェイ別の勝率・平均得点・平均失点を、既に取得済みのfixturesデータ
から追加のAPI呼び出し無しで計算し(`computeHomeAwaySplit`)、明確な差(勝率差
20ポイント以上)がある場合は毎日学習エンジンが「事実」として記録するように
しました。クラブLayer2プロフィールの`homeAwayNote`フィールドの根拠としても
渡しています。

**⑤ Memory Engineの強化(「昨日何を考えていたか」を実際に確認できるように)**

Memory Engine自体(`getConclusionHistory`による履歴保持)はStage Eから実装
されていましたが、これまでどのエンドポイントからも呼ばれておらず、実質的に
検証不可能でした(正直な弱点)。今回、新しいエンドポイント
`GET /api/knowledge/team-view-history?team=<英語クラブ名>` を追加し、
「今日の見解」と「過去の見解の履歴(いつ・なぜ変わったか)」を実際に確認
できるようにしました。

**⑥ Knowledge Engine(Layer2固定知識/Layer4振り返り)を議論モードの根拠に正式に接続**

これまでLayer2(クラブプロフィール)・Layer4(振り返り)はKnowledge Engineに
保存されるだけで、実は議論モードの根拠プール(`server/reasoning/evidencePool.js`)
には渡っていませんでした(取りこぼし)。今回、この2層も根拠プールに含める
ように修正しました。これにより、議論モードのAIの考察が、より多くの蓄積知識を
実際に参照するようになります。

**クラブLayer2プロフィールに追加したフィールド**: カウンター攻撃の活用傾向・
ボール保持の傾向(保持率という数値ではなく定性的な傾向)・ホーム/アウェイの
実データに基づくコメント、を追加しました(いずれも「AIによる推定」)。

**実装できなかった項目と、その理由・代替案(このラウンドの正直な回答):**
- **主要リーグ全クラブ・全選手の"毎日一括"更新**: 上記①の通り、オンデマンド
  方式(質問された相手から知識が蓄積される)に置き換えることで対応しました。
  「毎日決まった時刻に全クラブ・全選手が更新される」という意味での毎日更新では
  ない点にご注意ください(質問されない限り、その相手の知識は増えません)。
  **代替案**: どうしても特定の追加クラブ・選手を毎日確実に更新したい場合は、
  `server/learning/registeredTeams.js`への追加(クラブ)、または同様の
  registeredPlayers一覧を新設して毎日学習エンジンのループに組み込む(選手)、
  という形で対応できます。ただしAPI-Football無料枠(1日100リクエスト)を
  考えると、追加できる件数には限りがあります。
- **PPDA・xG・xGA**: 前回同様、API-Football側で確認できないため未実装です。
- **市場価値・契約情報(期間・年俸)・利き足**: API-Footballの選手オブジェクトに
  該当フィールドが存在しないことを確認済みです(id, name, age, birth,
  nationality, height, weight, injured, photo のみ)。**代替案**: Transfermarkt等の
  専門データソースとの契約が別途必要です(スクレイピングは既存方針により不可)。
- **プレス成功率**: PPDAと同様、API-Footballにこの種の高度な戦術指標はありません。
  **代替案**: タックル+インターセプトの合計を「守備指標」として代用しています。
- **空中戦だけの勝率**: API-Footballのデュエル(競り合い)データは地上戦・空中戦を
  区別しないため、「空中戦」ではなく正直に「デュエル(競り合い全体)勝率」として
  提供しています。
- **選手の複数シーズンにわたる怪我履歴**: 現在報告されている負傷者情報
  (クラブ単位、既存の`/injuries`)は引き続き利用できますが、選手個人の過去の
  怪我の詳細な履歴(いつ・何を・どれくらいの期間)は、選手ごと・シーズンごとに
  追加のAPI呼び出しが必要になり、オンデマンド方式のコスト設計と整合しないため
  今回は実装していません。
- **監督交代後の成績変化**(交代前後で的中率がどう変わったか): 監督遍歴の

`learn:weights`はまだ1度も更新されていません**(理由は④参照)。そのため

```
[毎日学習エンジン dailyJob.js] (現状: GitHub Actionsのcronはまだ未発火・手動実行1回のみ)
  │
  ├─① API-Footballの実試合結果 → フォーム/得点傾向/ホームアウェイ差
  │     → Knowledge Engine Layer1(事実)に保存 ……… 議論モードの根拠にのみ使用(点線)
  │
  ├─①b/①c → Knowledge Engine Layer2(クラブプロフィール・LLM生成)
  │         → Memory Engine(「今日の見解」を保存・前日と比較) ……… 議論モードの根拠にのみ使用(点線)
  │
  ├─② 保留中の自社予測を解決(試合終了を確認)
  │     → 的中/不的中を learn:ownpred:<id> に記録
  │     → Hypothesis Engine: 状態仮説が当たっていれば Knowledge Engine Layer4(検証済み分析)に昇格、外れれば破棄
  │     → Knowledge Engine Layer4(振り返り)に必ず記録(当たり/外れ問わず)
  │
  ├─③ 登録クラブの次の試合について新しい自社予測を作成 → learn:ownpred:<id> に保存(pending化)
  │
```

#### ⑨ 100試合・1,000試合・10,000試合積み重ねたら、本当に賢くなり続けますか？

正直な評価です。**「改善しても悪化した変更は採用しない」という安全装置
(バックテストで上回った場合のみ採用)がある設計自体は健全**で、これは
データが増えても壊れません。一方で、監査の過程で**本当に頭打ちを引き起こす
設計上の問題を1つ発見し、修正しました**。

- **発見した問題**: `learn:ownpred:recent`(バックテスト・勾配降下法の学習に
  使う実績データ)は`OWN_PRED_RECENT_KEEP = 30`件で`LTRIM`され、常に直近30件
  しか保持していませんでした。つまり100試合・1,000試合・10,000試合と検証を
  積み重ねても、モデルが実際に学習に使えるのは**常に直近30件だけ**で、
  古い実績は無条件に切り捨てられていました。これでは蓄積量に応じて統計的な
  確からしさが増すことはなく、直近の少数データのブレに毎回振り回されるだけ
  になり、「昨日より今日、今日より明日と賢くなる」設計にはなっていません
  でした。**修正**: 保持件数を300件に拡大しました(`server/learning/
  dailyJob.js`)。
- **残るリスク(今回は未修正・設計判断が必要)**: v1モデルのグリッドサーチは
  現在の重みの近傍を5パターンだけ試す単純な山登り法のため、大域的な最適値
  ではなく局所的な最適値に留まる可能性があります(v2の勾配降下法の方が
  この点は堅牢です)。また、1日あたり新規予測登録の上限が5件・登録クラブが
  11クラブという制約上、検証済みデータが実用的な件数(数十〜数百件)に
  育つまでには数ヶ月単位の時間がかかる見込みです。これはAPI-Football無料
  枠(1日100リクエスト)を守るための意図的な制限であり、有料プランに
  切り替えれば`OWN_PREDICT_LOG_CAP`/`OWN_PREDICT_RESOLVE_CAP`(`server/
  learning/dailyJob.js`)を増やすことで加速できます。

#### ① Prediction EngineにFailure Learning(外れた理由の分析)を追加

従来の学習ループ(試合終了→正解/不正解→重み更新)は「何故外れたのか」を
一切言語化していませんでした。`server/learning/predictionModel.js`に
`classifyFailureReasons(record, weights)`を追加し、予測を行った時点で
実際に使っていた特徴量(`features`)と重み(`weightsSnapshot`)だけを根拠に、
LLMを使わず機械的に理由を分類します。判定ロジックは2パターンのみ:

- **重視しすぎた**: その特徴量が予測した方向に強く効いていた(重みが一定
  以上ある)のに、実際の結果はその方向ではなかった(例:「過去対戦を
  重視しすぎた」「ホーム補正が強すぎた」)。
- **軽視した**: 実際の結果の方向を示す特徴量の値はあったのに、その重みが
  ほぼ0(＝まだ学習で重視されていなかった)ため予測に反映されなかった
  (例:「怪我人を軽視した」)。

どちらにも当てはまらない場合(古いv1形式のレコード等)は、正直に
「セットプレー・スタメン発表・審判の判定など、現在のモデルが数値化して
いない要因の影響」という限界を明示します(存在しない原因をでっち上げない)。

外れた理由は`record.failureReasons`として保存されるほか、Knowledge Engine
に`predictionFailureReason`(analysis)として単独保存され、議論モードの
根拠プール(`evidencePool.js`)からも参照できます。「次回の予測へ反映する」
というご要望への対応は二重に効きます: ①この失敗パターン自体が
`fitWeightsGradientDescent`(勾配降下法による重み再学習)の入力データ
そのものであり、既に重み更新に反映されている。②`summarizeFailureReasons()`
が直近の頻出理由を集計し、「AIの成長レポート」ウィジェットと成長ログで
可視化される(下記⑦参照)。テスト: `scripts/failure_learning_test.js`。

#### ③ Reasoning Engineを5仮説以上の比較方式に拡張

`server/reasoning/hypothesisGenerator.js`の観点(factor)を、従来の3つ
(怪我・移籍・戦術)から**9つ**に拡張しました: 怪我・出場停止/戦術・

疲労・ホームアウェイ差・勢いは、既に取得済みの`recentForm`データから
追加のAPI呼び出し無しで計算します(`computeFatigueNote`/

#### ④ Memory Engineの活用強化

2つの要望に対応しました。

**(a) 「以前はこう評価していましたが、今回評価を変えました」の言語化**:
Memory Engine自体(`memoryStore.js`)は既に変化検知・変化理由の記録を
実装済みでしたが、その情報がLLMの回答本文に確実に反映される保証が
ありませんでした。下記⑤の議論モード再設計にあわせて、システムプロンプトに
「前回の結論が与えられていて、かつ今回の結論が変わった場合は、②AI独自の
意見の中で必ず『以前は〜と評価していましたが、今回は〜に評価を変えました』
という趣旨の文を含めてください。前回の結論が無い、または今回と同じ場合は、
変化した体で書かない(でっち上げない)でください」という明示的な指示を
追加しました。

**(b) 試合予測の記憶(前回の予測・結果・外れた理由・学んだこと・次回改善点)**:
毎日学習エンジンの予測解決ループに、`memoryStore.saveConclusion()`への
書き込みを追加しました。サブジェクトキーは`team:<クラブ英語名>:predictionMemory`で、
内容は「対戦カード: 予測は◯◯ / 結果は◯◯(的中/不的中) / 外れた理由:
◯◯(①のFailure Learningの出力) / 学んだこと: ◯◯ / 次回改善点: ◯◯」を
1つの文章にまとめたものです。Memory Engineの既存の変化検知の仕組み
(内容が変われば自動的に前の内容を履歴へ退避する)をそのまま再利用している
ため、対戦カードが変わるたびに「前回の予測」が自動的に履歴として残ります
(`getConclusionHistory()`で取得可能)。テスト: `scripts/memory_prediction_test.js`。

#### ⑤ 議論モードの回答構成を再設計(検索AIから議論できるAIへ)

`POST /api/discuss`の出力形式を全面的に作り替えました。以前は
「###根拠### / ###考察### / ###結論### / ###フォローアップ###」という
「事実の要約」に近い構成でしたが、新しくは:

1. **一般論**(この話題について世間で一般的に言われている見方)
2. **AI独自の意見**(実データを踏まえたAI自身の見解。評価が変わった場合は必ず言及)
3. **反対意見**(AI独自の意見に対する、最も説得力のある反対の視点・懸念点)
4. **最終結論**
5. **今後どうなると思うか**
6. **最も重要だと考える点**(必ず「私は○○が最も重要だと考えます。」の1文)

という「議論の型」を毎回踏ませます。システムプロンプト(`buildDiscussSystemPrompt`)
で明示的にこの構造を指示し、`parseDiscussLlmOutput`で各セクションを
パースして、レスポンスの`generalView`/`aiOpinion`/`counterArgument`/
`finalConclusion`/`futureOutlook`/`mostImportantOpinion`フィールドとして
返します(旧`evidence`/`consideration`/`conclusion`から名称・構成を刷新。
既存の呼び出し元がある場合は移行が必要です)。ホーム画面のチャットUI
(`renderDiscussReplyHtml`)もこの6要素をそれぞれ見出し付きで表示するよう
更新しました。テスト: `scripts/server_discuss_test.js`、
`scripts/server_discuss_reasoning_memory_test.js`。

#### ⑥ AIマッチ分析を11項目のフル分析に拡張

第12章時点で①勝率②予想スコア③試合展開⑤キープレイヤー⑥怪我人の影響
⑧逆転シナリオ⑨AIが最も重要視した要素⑪AIの結論の8項目は実装済みでした。
このフェーズで新たに:

- **⑦戦術相性**: 両クラブの直近フォーメーションが揃っている場合、中盤の
  人数差・最終ラインの人数差から機械的に相性の見立てを組み立てる
  deterministicなフォールバック(`tacticalCompatibility`)を実装し、LLM
  利用可能時はより自然な文章に置き換えます。これはAPI-Footballの実データ
  そのものではなく「AIの見解」であるため、本文に必ずその旨を明示します。
- **⑩この試合最大の見どころ**: 過去対戦の蓄積・両クラブの得点源対決・
  負傷者数・順位差など、実際に取得できたデータの中から最も話題性が
  高そうな1点を機械的に選ぶ(`biggestHighlight`)。

これで11項目中10項目が実装済みです。唯一実装を見送ったのは:

- **④鍵になる時間帯**: `/fixtures/events`(ゴールの発生分数)の集計が必要です。
  このエンドポイントはオンデマンド(利用者が呼ぶたびに実行される、回数の

  API-Football無料プランの1日100リクエスト枠を容易に超えるリスクがあります。
  **代替案**: ②の「得意な時間帯・苦手な時間帯」と同じデータソースのため、

  事前集計し、Knowledge Engineの`fact`として溜めておき、AIマッチ分析は
  その蓄積済みデータを読むだけにする設計が現実的です。今回はコスト超過
  リスクを避けるため見送りました。

テスト: `scripts/server_match_analysis_test.js`。

#### 見つかった根本原因

これまで「この聞き方にはまだうまくお答えできませんでした」「うまく認識でき
ませんでした」が頻発していた原因は、Phase 1〜3で作り込んだPlanner→RAG→
Reasoning Engine→LLMの議論エンジン(`/api/discuss`)自体の性能不足ではなく、
**フロントエンド(index.html)のルーティングが、その議論エンジンをごく一部の
「議論トリガー」フレーズ(「〜だと思う」「なぜ」等)にしか使っていなかった**
ことでした。それ以外の全ての質問は、ローカルに登録された100人程度の選手
データ・11クラブのみを対象にした、質問の角度を区別しない狭いルールベース
関数(`answerPlayerQuestion`/`buildClubAnswer`)に渡され、パターンに一致しな
ければ即座に固定の失敗文言を返して終わっていました。裏側の`/api/discuss`は
実際にはクラブ・選手(API-Football実検索、ローカル未登録でも可)・一般論の
どのケースでも実データに基づいた考察を返せる設計に既になっていたにも
関わらず、ほとんどの質問がそこへ到達できていなかった、という構造的な問題
です。

#### 実施した修正(index.html)

- **NO_RULE_MATCHエスカレーション方式の導入**: `answerPlayerQuestion`と、
  新設した`answerClubQuestion`は、パターンに一致する「よくある聞き方」だけ
  無料・即答し、一致しない場合は失敗文言ではなく`NO_RULE_MATCH`という内部
  シンボルを返すように変更しました。呼び出し側(`heroAskAI`/`sendChatMessage`)
  は必ずこれを判定し、一致しなければ`runDiscussFlow`(実データ+LLMの議論
  エンジン)へエスカレーションします。「答えられない」がそのままユーザーに
  見えることはもう無く、必ずAIが実際に考えようとします。
- **`answerClubQuestion`の新設**: 従来の`buildClubAnswer`は質問の角度(なぜ
  強い/最近弱くなった/補強すべきか等)を一切区別せず、常に同じ静的な要約文を
  返していました(=事実上、質問に答えていなかった)。素朴な「クラブ概要を
  知りたい」聞き方だけは即答を維持し、実データの裏付けが必要な角度の質問は
  正直に議論エンジンへ委ねるよう設計を変えました。
- **未登録選手の推測(`guessUnregisteredPlayerName`)**: これまでローカルの
  選手カードに登録されていない選手は、質問文からそもそも「選手についての
  質問だ」と検出すること自体ができませんでした。サーバー側
  (`handlePlayerSeasonStats`)は選手名さえあればAPI-Footballへ実際に検索を
  かけられる設計だったため、質問文からカタカナ表記の選手名(海外選手の大半)
  や、よく話題になる代表的な日本人選手の姓(簡易辞書、拡充可能)を推測し、
  ローカル未登録の選手についても実データに基づく回答を試みるようにしました。
- **「主題なし」の質問も諦めない**: クラブ・選手のどちらも検出できない質問
  (例:「今日強いクラブは？」「ベストイレブン組んで」)も、以前は即座に固定
  文言で終わっていましたが、今は`subject: null`として議論エンジンへ渡し、
  一般的なサッカー知識に基づく実際のAI考察を返します(信頼度は正直に低めに
  表示されます)。
- **試合系の質問文の認識を拡張**: 「この試合どっち勝つ？」のように対戦相手が
  特定できない質問でも、これまでの固定失敗文言ではなく、本日のAIおすすめ
  対戦を表示した上で「クラブ名を含めて聞いてください」と具体的に案内する
  形に変更しました。

`/api/growth-log`の生データ(`facts`配列に16件の実際の事実が含まれていたに
も関わらず`knowledgeItemsSavedToday`は0、`knowledgeItemsDuplicateToday`は
16)を突き合わせて調査した結果、**症状は1つでしたが、原因は2つ**あることが
分かりました。「エラーが出ているだけ」ではなく、両方とも根本原因まで特定し
修正しています。

#### 主因: 同じ日に学習エンジンが2回実行されると、1回目の実績が2回目の結果で隠れてしまう

Renderの無料プランはアクセスが無いとスリープし、起床に数十秒かかります。
`.github/workflows/daily-learning.yml`は、1回目のリクエストがタイムアウト
すると60秒待って自動的にもう一度呼び出す設計になっていますが、1回目の
リクエストは(GitHub Actions側ではタイムアウトしていても)Render側では
処理が最後まで完了していることがあります。この場合、同じ日に学習エンジンが
実質2回実行されることになります。

従来は`run-daily`を実行するたびに、その日の学習ログ
(`learn:growthlog:<日付>` / `learn:growthlog:latest`)を**まるごと上書き**
していました。1回目の実行で実際に新しい知識が16件保存されていても、2回目の
実行(内容は同じ試合結果を見るので、計算される事実も同一になり、Knowledge
Engineの重複排除により正しく「重複」と判定される)の結果でまるごと上書き
され、「今日追加した知識0件」という誤解を招く表示になっていました。
**Knowledge Engine自体の重複排除ロジックは正しく機能しており、データが
壊れていたわけではありません。**「その日の実行の合計」ではなく「直近1回の
実行結果」を見せていた、集計・表示側の設計ミスでした。

`server/learning/dailyJob.js`に`mergeGrowthLogs()`を新設し、同じ日付の
既存ログがあれば、件数(知識保存数・検証試合数・新規予測数・仮説の的中/破棄・
AIの見解変化数など)を合算し、事実の一覧は内容(statement)で重複排除して
連結し、モデルの状態を表す値(的中率・重み更新の有無等)だけは最新の実行の
値を使うようにしました。あわせて`runsToday`(その日の実行回数)を新設し、
2回以上実行された日は「AIの成長レポート」ウィジェットにも正直にその旨を
表示します(ℹ️ 本日は学習エンジンが2回実行されました)。

#### 副因: `team_not_found:Al-Nassr` ― 一時的な障害と「本当に見つからない」を区別していなかった

`resolveTeamId()`(クラブ名→API-FootballのチームID変換)は、API-Football
呼び出しが「本当に該当チームが無かった(空の検索結果)」のか「一時的な
ネットワーク障害・API側のタイムアウト等で例外が発生した」のかを区別せず、
どちらも同じ扱いで24時間キャッシュしていました。後者(一時的な障害)まで
24時間「見つからなかった」ことにしてしまうと、次にそのクラブを扱おうと
する処理が丸1日ずっと失敗し続けることになります。

修正では、この2つを明確に区別しました。API呼び出しで例外が発生した場合は
最大1回、短い間隔を空けて自動的に再試行し、それでも失敗した場合は
キャッシュせずにnullを返します(次回の呼び出しでまた挑戦できるようにする
ため)。「本当に見つからなかった」(全ての表記ゆれのバリエーションを試しても
空の結果だった)場合だけキャッシュ対象にし、キャッシュ時間も24時間から
3時間に短縮しました。

なお、この修正作業の過程で、**もう1つ別の、より根本的なキャッシュの不具合**
を発見し、あわせて修正しました。`cacheGet()`は「キャッシュに無い」場合と
「キャッシュされた正しい結果がnullだった」場合の両方でnullを返す実装に
なっていたため、呼び出し側の`if (cached !== null) return cached;`という
判定では両者を区別できず、「本当に見つからなかった」結果の負のキャッシュ
(`cacheSet(key, null, ...)`)が**実質的に一度も機能していませんでした**
(常にAPIへ再フェッチしていました)。この不具合は`resolveTeamId`だけでなく
`resolvePlayerId`(選手検索)にも影響していたため、`cacheGet()`が「キャッシュ
に無い」場合は`undefined`を返すよう修正し、両方の呼び出し箇所を
`!== undefined`判定に統一しました。これは今回作った新しいテスト
(`scripts/production_bug_fix_test.js`)がなければ見つけられなかった、
既存の潜在バグです。

#### テスト

  (このテストが、上記の`cacheGet`の潜在バグを実際に検出しました)

### 16. 2026年8月・本番調査で発見した「fetch()に時間制限が無い」構造的な弱点の修正

上記15番の修正版をGitHubへアップロード・Renderへデプロイしていただいた後、
「治ってないです」というご報告をいただき、本番環境を直接調査しました。

調査の結果、まず判明したのは**アップロード自体は正しく完了しており、
`server.js`・`index.html`・`learning/dailyJob.js`はすべて最新の修正版が
GitHub/Renderに反映されていた**ということでした(自動取得ツールで大きな
ファイルの中身を確認した際に、一時的に「反映されていない」という誤った
判断をお伝えしてしまう場面がありましたが、最終的にSaiさんご自身の画面上の
検索で確認いただき、正しく反映済みであることを確認できました)。

にもかかわらず、GitHub Actionsから「Daily Learning Engine」を手動実行すると、
2回連続で約7分後に`exit code 28`(curlのタイムアウト)で失敗しました。
これは新たに発生していた、15番とは別の不具合です。

#### 根本原因: 外部APIへのfetch()呼び出しに一切タイムアウトが設定されていなかった

このプロジェクトはサッカーデータAPI(API-Football)・Upstash(Redis)・
Anthropic LLMの3箇所でNode.js標準の`fetch()`を直接呼んでいましたが、
いずれも呼び出し時間の上限(タイムアウト)を一切設定していませんでした。
そのため、外部API側が何らかの理由で応答を返さない状態(ネットワーク障害・
相手サーバー側の異常等)に陥ると、そのリクエストは**永遠に**待ち続けて
しまい、日次学習エンジン全体がフリーズする構造的な弱点がありました。

15番で実装した「一時的な障害を検知して自動リトライする」仕組み
(`searchTeamsWithRetry`)自体は正しく実装されていましたが、個々の
`fetch()`呼び出しに時間の上限が無ければ、「一時的な障害が発生した」こと
自体を検知すること(=例外としてcatchされること)ができず、この仕組みが
機能する前提条件が満たされていませんでした。

#### 修正内容

`AbortController`を使った`fetchWithTimeout()`ヘルパーを新設し、3箇所すべての
`fetch()`呼び出しに明示的なタイムアウトを設定しました。上限を超えた場合は
`err.code = "TIMEOUT"`を持つエラーとして確実に失敗するようになり、既存の
再試行・エラー収集ロジックが正しく機能するようになります。

- `server.js`の`callApiFootball`(サッカーデータAPI): 20秒
  (環境変数`API_FOOTBALL_TIMEOUT_MS`で上書き可能)
- `server.js`の`upstashCmd`(Upstash Redis): 15秒
  (環境変数`UPSTASH_TIMEOUT_MS`で上書き可能)
- `server/llm/providers/anthropic.js`の`generate`(Anthropic LLM): 30秒
  (環境変数`ANTHROPIC_TIMEOUT_MS`で上書き可能。LLMは生成に時間がかかることが
  あるため、他の2つより長めに設定)

これにより、外部APIがどれだけ長く応答しなくても、日次学習エンジンは
決められた時間内に必ず処理を打ち切り、その箇所だけをエラーとして記録した
うえで残りの処理を続行できるようになりました(既存の「1クラブ・1選手ずつ
try/catchで囲み、失敗しても`errors`配列に記録して次へ進む」という設計が、
ようやく本来意図した通りに機能するようになったとも言えます)。

#### テスト

(ハングする)」状況を疑似的に再現し、以下を確認しています。実際に20〜30秒

### 17. 2026年8月・根本原因の特定と対策(GitHub Actionsのタイムアウトと、日次ジョブの実処理時間の構造的なミスマッチ)

3回とも失敗までの時間が約7分と非常に安定していたことから、「外部APIが
不規則にハングしている」のではなく、**GitHub Actionsのcurlが待てる時間
(1回の呼び出しにつき最大2分、これを内部で最大3回試行するため合計約7分)を、
日次学習エンジンの実際の処理時間(11クラブぶんのAPI呼び出し・LLMによる
見解生成などを順番に処理するため、本番の実データでは数分かかりうる)が
超えてしまっている**という、クライアント側の「待てる時間」とサーバー側の
「実際にかかる時間」の構造的なミスマッチが真の原因だと判断しました
(16番のタイムアウト修正は、個々の外部API呼び出しが本当にハングした場合の
保険として引き続き有効ですが、今回のように「ハングはしていないが、単に
処理全体に時間がかかる」ケースには対応できていませんでした)。

#### 修正内容: `/api/learning/run-daily` を「即座に応答→処理はバックグラウンドで継続」する方式に変更

これまでは、このエンドポイントは学習ジョブが完全に終わるまでHTTPの応答を
返しませんでした。これを、リクエストを受け取ったら即座に
`{"ok":true,"started":true,...}`という応答を返し、実際の学習処理は
レスポンスを待たずにサーバー側でバックグラウンド実行を継続する方式
(fire-and-forget)に変更しました。これにより、学習処理に何分かかっても、
呼び出し側(GitHub Actionsのcurl)のタイムアウト設定の影響を一切受けなく
なります。同時に、同じジョブが二重に起動してしまわないよう、実行中フラグに
よる二重起動防止も追加しました。

デバッグ・動作確認用に、`?sync=1`を付けて呼び出すと従来通り処理完了まで
待ってから完全な結果を返す同期モードも残してあります
(例: `POST /api/learning/run-daily?key=<秘密のキー>&sync=1`)。

`.github/workflows/daily-learning.yml`も、この変更に合わせて2段階の構成に
更新しました。

1. まず呼び出して「開始できたか」だけを確認する(以前より高速に完了する)
2. その後、最大6分間30秒おきに`/api/growth-log`を確認し、実行時刻
   (`ranAt`)がこのステップを開始した時刻より後に更新されているかを見て、
   バックグラウンドの処理が実際に完了したことを確認する(これが無いと、
   「呼び出しには成功したが実際には裏で失敗していた」ことに誰も気づけない
   ため、単に「開始できた」だけでなく「本当に完了した」ことまで確認する
   設計にしました)

#### テスト

`scripts/server_learning_routes_test.js`を更新し、以下を確認しています。

- `POST /api/learning/run-daily`が処理完了を待たず、2秒未満で即座に
  `{"ok":true,"started":true}`を返すこと
- その後バックグラウンドで処理が実際に完了し、`/api/growth-log`に
  正しく反映されること
- `?sync=1`を付けた場合は、従来通り同期的に完全な結果(`teamsAnalyzed`等)
  が返ること(デバッグ用の同期モードが引き続き機能すること)

既存の全自動テスト(60本超)もあわせて再実行し、この変更で仕様が変わった
`server_learning_routes_test.js`以外は全て無変更で通過することを確認して
います。

#### 残課題

この修正により、GitHub Actions側は「学習ジョブが本当に完了したか」を
以前より正確に確認できるようになりましたが、日次学習エンジン自体の処理に
実際どれくらいの時間がかかっているかは、Renderのサーバーログに直接
アクセスできる立場ではないため厳密には把握できていません。今後もし
「6分待っても完了が確認できない」というエラーがGitHub Actionsで発生する
ようであれば、それは処理時間がさらに伸びている(または本当に何かが壊れて
いる)サインなので、その際はRenderのダッシュボードの「Logs」タブを確認
いただくか、私にログの内容を共有していただければ追加調査します。

#### ④試合を「開始前/試合中/終了」で整理

`classifyFixtureStatus()`を新設し、API-Footballが返すステータスコードを
以下の3分類(+延期/中止等の「その他」)に振り分けます。

- 試合中(🔴 LIVE): `1H`/`HT`/`2H`/`ET`/`BT`/`P`/`SUSP`/`INT`
- これから(⏰): `NS`/`TBD`
- 終了(✅): `FT`/`AET`/`PEN`/`AWD`/`WO`

「本日の実際の試合」カードは、この3分類ごとにセクションを分けて表示します
(試合中→これから→終了の順。終了した試合は折りたたみ表示で、必要な時だけ
「▼ 終了した試合を表示」で開けます)。各試合の行にも状態バッジ(🔴 LIVE
など)を表示します。

あわせて、`/api/fixtures/analysis`エンドポイント自体も拡張しました。従来は
「終了」した試合だけ実際の選手評価・イベントタイムラインを取得し、それ
以外(試合中も含む)は「開始前」と同じ静的なプレビューしか出していません
でした。今回、試合中の場合もAPI-Footballから取得できる「その時点までの
実データ」(得点・イベント・出場選手の評価)を取得して表示するように
しました。試合が終わっていない以上、「何が勝敗を分けたか」のような結論
めいた文章や最終的なMOTM判定は出さず、「まだ結果は確定していません」と
明記した上で「現時点までの状況」として見せる設計にしています(でっち上げ
防止)。試合中データはキャッシュを60秒と短くし、頻繁に開き直せば最新に近い
状況が見られるようにしました。

#### ③試合展開の「90分ストーリー予想」

`build90MinStoryHtml()`を新設し、試合前プレビューに「序盤(0〜30分)」
「中盤(30〜70分)」「終盤(70〜90分+)」の3フェーズに分けたストーリー
予想を追加しました。

**重要な設計方針**: 「〇〇分に△△が得点する」のような架空の具体的な出来事は
一切でっち上げません。あくまで登録選手の実データ(能力値)から読み取れる
「起こりやすい傾向」を、確率的な言い回し(「〜が鍵になりそうです」「〜の
展開になりやすいと考えられます」)で言語化しています。

- 序盤: 両クラブの総合力差や、スピードタイプの選手の存在から、立ち上がりの
  主導権の傾向を予想
- 中盤: 拮抗しているか否か、パス・戦術眼の高い選手(ゲームメイク役)に注目
- 終盤: 運動量が落ちる時間帯の傾向、決定力の高い選手にとってのチャンスの
  増加、拮抗している場合はセットプレー等の一発の重要性に言及

片方のクラブしか登録データが無い場合はその旨を明記した参考程度の予想とし、
両クラブとも未登録の場合は何も生成しません(既存の「データが無いものは
語らない」という一貫した方針を踏襲)。

ご要望原文: 「プレミアリーグ・セリエA・ラ・リーガ・ブンデスリーガ・リーグ・アン・

#### 必須リーグ(毎日)と拡張リーグ(ローテーション)の分離

API-Football無料プラン(1日100リクエスト)を前提にすると、リーグ1つあたり
3リクエスト(順位表・得点ランキング・アシストランキング)かかるため、ご要望の
10リーグすべてを毎日フル取得すると30リクエスト/日になります。既存の日次学習
(登録11クラブの分析等)だけですでに最大50〜70リクエスト/日を使っているため、
10リーグ×毎日では無料枠を超えるリスクが高いと判断しました。

そこで、ご要望文の「最低でも」という表現に従い、以下のように分離しました。

- **必須5リーグ(`MANDATORY_LEAGUES`、毎日必ず取得)**: プレミアリーグ・
  ラ・リーガ・ブンデスリーガ・セリエA(イタリア)・リーグ・アン。15リクエスト
  /日。
- **拡張5リーグ(`EXTENDED_LEAGUES`、日付ベースのローテーションで2件/日)**:
  メジャーリーグ・サッカー・カンピオナート・ブラジレイロ・セリエA(ブラジル)・
  チャンピオンシップ(イングランド)・プリメイラ・リーガ・スュペル・リグ。
  6リクエスト/日。5リーグを2件/日で回すため、3日弱ですべて一巡します。

合計で優先順位⑥分は最大21〜25リクエスト/日程度(リーグID未解決時のみ発生する
`/leagues`検索を含む。一度解決したIDはUpstashに永続キャッシュするため、翌日
以降は追加リクエストなし)。既存の50〜70リクエスト/日と合わせても、無料プラン
の100リクエスト/日以内に収まる設計です。ただし余裕は大きくないため、今後
機能を追加する際はこの合計値を都度確認してください。

#### リーグIDの扱い(でっち上げない)

欧州5大リーグのID(39/140/78/135/61)は、このコードベース(`server/server.js`
の`DEFAULT_LEAGUES`/`SEARCH_LEAGUES`)ですでに実際のAPI-Footballへの問い合わせ
で動作確認済みの値をそのまま再利用しています。一方、拡張5リーグのうち
メジャーリーグ・サッカー(253)以外の4リーグは、このコードベースでID未確認
でした。誤ったIDを決め打ちすると「存在しないリーグのデータを取得しようと
して常に空振りする」というでっち上げに近い不具合になりかねないため、
`resolveLeagueId()`(`server/learning/leagueConfig.js`)がAPI-Football自身の
`/leagues?name=&country=`検索によってIDを解決し(既存の`resolveTeamId`と同じ
設計)、解決できたIDはUpstashに永続キャッシュします。解決できなかった場合は
架空のIDを作らず、正直に`league_id_unresolved:...`というエラーを記録した上で
そのリーグをスキップします。

#### Knowledge Engineの一般化(クラブ単位→クラブ/リーグ単位)

これまで`server/knowledge/knowledgeStore.js`は`item.teamEn`を必須としており、
クラブ単位の知識しか扱えませんでした。リーグ単位の知識も同じ仕組み(重複
排除・失効管理)に乗せるため、`entityKeyFor(item)`というヘルパーを追加し、
`item.teamEn`があればそれを、無ければ`` `league:${item.leagueEn}` ``を
エンティティキーとして使うよう一般化しました。既存のクラブ単位の呼び出しは
完全に後方互換です(`scripts/knowledge_store_test.js`が無変更で全通過する
ことで確認済み)。

同名だが国が異なるリーグ(例: セリエAはイタリアとブラジルの両方に存在)を
混同しないよう、リーグのエンティティキーには必ず国名を含めています
(`leagueEntityKey`: `` `${nameEn} (${countryJa})` ``)。

**重複排除の設計で自分自身のバグを発見・修正した点**: 順位表・ランキングの
文章(`formatStandingsStatement`/`formatTopListStatement`)を実装した際、
最初は文中に日付を埋め込んでいました(例:「2026-08-04時点の順位表」)。
Knowledge Engineの重複排除は「文章の内容そのもの」をハッシュ化して判定する
仕組みのため、日付を埋め込むと、実際には順位表が前日と一切変わっていなくても
毎日「新しい事実」として扱われてしまい、「本当に変化があった時だけ知識が
増える」という設計そのものが壊れることに実装中に気づき、修正しました。
現在は他の事実生成コードと同じく、文中に日付を含めず、「いつの情報か」は
`computedAt`/`firstSeenAt`/`lastSeenAt`というメタデータ側だけで管理して
います。

#### 「更新できなかった項目は理由を残す」— 今回の実装の中心

ご要望の16項目それぞれについて、**取得できた値**か、**取得できなかった理由**の
どちらかを必ず記録します。理由は3種類に分類し、利用者が「明日は取れるのか、
それとも構造的に無理なのか」を区別できるようにしました。

| 分類 | 該当項目 | 表示のされ方 |
|---|---|---|
| (a) データソースに構造的に存在しない | 利き足・市場価値・契約 | 「現在のデータソースでは更新できない項目」として、代替案つきで開示 |
| (b) 今日はAPI予算が足りず見送った | その時々 | 「明日再試行する項目」として開示 |
| (c) 今日のAPI呼び出しが失敗した | その時々 | 同上 |

(a)の3項目については、API-Footballの`/players`レスポンスの`player`オブジェクトが
`id/name/age/birth/nationality/height/weight/injured/photo`しか持たないことを
確認済みです(この事実は既存の`server/learning/playerFeatures.js`の冒頭に、
以前の調査結果として記録されていたものをそのまま根拠にしています)。
そのため「毎日APIから更新する」ことが構造的に不可能であり、推測値をAIに
作らせることもしません(実データでないものを事実として保存しないという
既存の方針のため)。代わりに、Transfermarkt系の別データソースが必要である旨と、
優先順位⑪のAPI比較で検討対象にしている旨を理由に明記しています。
なお、アプリ内には手動登録された利き足・契約データが存在するため、
「APIからは更新できないが、手動データではこうなっている(最新性は保証されない)」
と正直に併記します。手動データが無い選手には、存在しない参考値をでっち上げません。

**「評価推移」の作り方(追加のAPIコスト0で、毎日必ず情報が増える部分)**:

なります(このプロジェクトの最優先目標に直結する設計です)。初回は

名/日(既定3名)のローテーションとし、**予算が増えれば環境変数を上げるだけで
自動的に増やせる**設計にしました(優先順位⑪で有料APIへ移行した場合、
コード変更なしでスケールします)。

ご要望原文: 「今日追加した知識0件・検証0件 と表示されることがあります。これでは

#### 調査結果: 「0件」には性質のまったく違う2つの原因があった

コードを追いかけた結果、根本原因が判明しました。**「0件」表示には、正常な0件と
異常な0件の2種類があり、これまでのUIはその区別をまったくしていませんでした。**

- **(A) 正常な0件**: Knowledge Engineは「内容が本当に変わった時だけ」新しい知識と
  して数える設計です(重複排除)。順位表も選手データも前日から変化がなければ、
  **正しく動いていても新規0件になります**。これは「同じ情報を毎日水増しして
  『学習している風』に見せない」という、このプロジェクトが最初から持っている
  誠実な設計の裏返しです。しかし画面には「0件」としか出ないため、
  利用者からは「サボっている」ようにしか見えませんでした。
- **(B) 異常な0件**: APIキー未設定・Upstash未設定・**API予算切れ**・GitHub Actions
  が動いていない、などで本当に何もできていない状態。

つまり、コードそのものが壊れていたのではなく、**「正常に動いていることを利用者に
伝える機能が欠けていた」**のが本質的な問題でした。あわせて、優先順位⑦で新設した
APIリクエスト予算ガードにより、(B)のうち最も気づきにくい「1日100リクエストの
上限に静かに到達していた」ケースも検出・表示できるようになりました。
